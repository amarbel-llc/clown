# clown#241 and clown#288: design notes with recommendations

Status: **ruled 2026-11-12, implemented in part.** #241: option A plus a
record, wake and log resource for every started server (merged: the
death log line, then `server_exit` records and the `.../log` resource); no
restart, B stays later. #288: threat model is other local users and confined
processes; the bridge-side `CLOWN_BRIDGE_TOKEN` slice, `/healthz` left open and
the two ADR 0006 corrections are done; the host minting the token and the
manifest `headers` are not, and the unix-socket option is a separate issue.
The text below is the original proposal, unchanged. Claims are **R** (read in code in this worktree) or **I**
(inferred, not checked) unless marked otherwise. Related: FDR 0002 (the stdio
bridge), ADR 0006 (the bridge trusts loopback clients), FDR 0020 (agent
scope), `docs/plans/2026-11-06-clown-344-disconnect-record.md`.

## clown#241: the plugin host neither restarts nor surfaces a dead child

### The problem, and how much of it is already answered

The issue (filed after a 2026-09-22 session where `just --mcp` died and the
agent found out ~50 minutes later) asks for restart, surfacing, or at least a
better error. Since then clown#344 landed the surfacing half. Read in code:

- The bridge writes a disconnect record for each end it can see, fails the
  calls in flight with a JSON-RPC error naming the record (`awaitend.go`,
  `record.go`), and the frontend wakes the session once per new record
  (`cmd/clown/disconnects.go`, `watchDisconnectWakes`). The session can read
  the record as an MCP resource (`clown-builtin-diagnostics/disconnects`).
- The host watches **recording bridges** and writes a `bridge_exit` record
  for a bridge that dies without the bridge having recorded it
  (`pluginhost/record.go`, `WatchExits`).

What is still true of the issue as written (R):

1. **No restart.** The bridge exits after its child dies (FDR 0002 "Crash
   behavior": "The bridge stays a transport adapter, not a supervisor"; the
   `restart` field is listed under Future Work). A `/mcp` reconnect then
   lands on a refused port, exactly as the issue observed. #344's note says so
   too ("No restart of a dead child").
2. **Only recording bridges are watched.** `WatchExits` skips servers that are
   not recording bridges or are reserved (`record.go:95`). A server the host
   starts itself that is not a bridge (a native `httpServers` plugin with its
   own command, the aggregator) that dies mid-session produced no log line
   until `Stop` at session end (`server.go`, `Stop` logged "died unexpectedly"
   only from its early `<-s.done` branch). Nothing woke the session either.
3. **The error a caller gets after the death, with nothing in flight,** is
   still claude's own "Unable to connect" (clown does not control that text);
   the wake is the clown-side answer, and whether it reaches an idle session
   in practice is unmeasured (I did not run #344's planned live check).

Gap 2 is cheap and uncontroversial; gap 1 is the real decision.

### Options

**A. Surface only (done, plus the slice below).** Cost: nothing more than the
slice. Leaves every transient child crash a permanent outage for the session,
as the issue complains.

**B. Bridge-level restart (FDR 0002's deferred `restart: never|on-failure|always`).**
The bridge keeps its listener (so its port, and claude's manifest URL, stay
valid) and respawns the wrapped child with backoff and a cap. Needs, at
least: re-running the MCP `initialize` handshake against the new child with
the client's cached parameters (the translator is a JSON-RPC pipe and does not
hold MCP session state today; **I**, not read in detail), failing the calls in
flight at the crash (never retrying them: a call may have had side effects),
telling claude the tool list may have changed, a record per death plus a note
that it was restarted, and a restart budget (say 3 in 60 s) after which the
bridge exits as today. Per server opt-in; default `never`, so no behaviour
changes for anyone who does not ask. Cost: medium. Risk: a restarted child
loses its in-memory state, so a stateful server looks healthy but has forgotten
its session; the record and wake must say "restarted", not hide it.

**C. Host-level restart (respawn the bridge from `pluginhost`).** A new bridge
gets a new ephemeral port, but claude holds the old URL in its manifest, so
the host would need a stable front address (a host-side relay or a fixed
socket path) in front of every bridge. Cost: large, and it adds a hop on every
call for the benefit of the rare crash. Not recommended.

### Recommendation

Do A now (below), then B as a per-server opt-in, `restart: on-failure`,
default `never`, with the budget above. C only if B proves insufficient.
Surfacing stays on regardless of the restart policy, as the issue itself says
("even a deliberate no-restart policy would be much less costly if the death
were visible").

### Smallest first slices

1. **Done in this change:** `ManagedServer.reap` logs "plugin server died
   unexpectedly" (exit code, signal) at the moment of death when the host did
   not ask for the stop, and `Stop` no longer logs it a second time. This
   closes gap 2's missing log line for every started server; it changes no
   behaviour besides one more log line. Test:
   `TestManagedServer_DeathIsLoggedWhenItHappens`.
2. **Next, small, behind a ruling on scope:** extend `WatchExits` to non-bridge
   started servers and write a record for them, so they get the wake too.
   Needs the record writer to accept a server that is not a bridge
   (`recorded()` gates on the bridge's record directory today).
3. **B, first cut:** parse and validate `restart` on `stdioServers` (no
   behaviour), then the bridge's respawn loop for `on-failure` with the
   budget, then the initialize replay. Each is its own commit.

### Questions for the operator

1. Is a per-server opt-in restart acceptable, or should a restart policy be
   global with a per-server opt-out?
2. Should a restarted server wake the session ("restarted, in-memory state
   lost"), or only record it?
3. Do non-bridge started servers (native `httpServers`) deserve the same
   record and wake as bridged ones?

## clown#288: the bridge's loopback listener accepts any local process

### The problem, located in code

`clown-stdio-bridge` listens on `127.0.0.1:0` (`main.go`, `listen`) and serves
`/mcp`, `/healthz` and the control routes `/clown/system-prompt`,
`/clown/exclude-tools`, `/clown/shutdown` (`routes.go`). On loopback TCP there
is no caller check at all; the only gate is `mcphttp.ValidateOrigin`, which
refuses a browser-style `Origin` that is not loopback and **permits an empty
Origin** (`mcphttp/server.go:567`), so any non-browser local client passes.
The issue's repro (connect from another process, send `initialize`, get an
answer) follows from this reading (R); I did not run it.

Two statements in ADR 0006 do not hold as written (R, **I** for the second):

- "the port is ... announced only to the parent process via a private stdout
  handshake". The port is not secret: any local user can list listening
  sockets. A same-host process that wants it can find it.
- "A local attacker who can reach the listener can already do worse things."
  True for a process running as the same user. It is not true for another
  user on a shared host, nor for a process confined from reading the user's
  files (an agent unit): both can reach loopback but cannot read the manifest
  or the bridge's environment.

What an attacker gets by connecting: everything the wrapped server's tools do,
as the session, and, through the control routes, the ability to read or clear
the session's tool exclusions (`/clown/exclude-tools`, which is how
`--cheap-context` hides tools; a caller who clears it un-hides them, though
`handleMCP` also refuses excluded calls) and to fetch the system-prompt
fragment. On the unix-socket mode (agent scope) this is already handled:
`--listen-unix --peer-unit` admits only the agent unit and the parent clown via
`SO_PEERCRED` (`internal/0/peercheck`), and `frontendOnly` refuses the unit on
the control routes (clown#301). So the exposure is the **unconfined** loopback
mode only.

### Options

**A. Per-session bearer token.** The host generates a random token per bridge
(or per session), gives it to the bridge through its environment, sends it on
its own requests (`/healthz`, the control routes, `/clown/shutdown`), and puts
it in claude's manifest entry as an `Authorization` header. The bridge answers
401 to any request without it (constant-time compare), `/healthz` included.
Costs: `MCPServerEntry` (`config.go:314`) has `Type`, `URL`, `Timeout` and no
headers, so it grows a `headers` field, and this depends on the pinned claude
(2.1.318) honouring `headers` on `http` entries, which I have **not** verified
and must before anyone relies on it. The token sits in the manifest file in the
staging directory, so its permissions matter (0600 in a 0700 directory; the
staging root already is, **I**). Same-user attackers are not stopped, because
they can read the manifest, the same limit ADR 0006 already accepts. Cost:
small to medium. Protects against other users on the host, and against
processes that cannot read the staging directory.

**B. Unix socket with peer credentials for every bridge.** `peercheck` and the
bridge's `--listen-unix` mode exist. But claude's HTTP MCP client takes a URL,
not a socket path, which is why agent scope puts an in-unit relay in front
(`RouteManifestThrough`, FDR 0020 F12). Doing this everywhere means a relay
process per session on the unconfined path as well. It checks the caller's
uid (and, in agent scope, its cgroup/unit), which is stronger than a token
against a process that merely learned a secret. Cost: large; it also adds a
hop and a process to every unconfined session for a modest threat.

**C. Keep loopback, record the threat model.** Amend ADR 0006 to say what is
and is not defended (other users and confined processes are out of scope on a
single-user developer host), correct the two statements above, and keep
`mcp` and the control routes as they are. Cost: none. This is a decision, not
a fix: the issue's expected behaviour ("rejects peers that cannot prove they
are the launching clown") is not met.

**D. Check the peer's uid from `/proc/net/tcp`.** Linux-only, racy, and
unavailable on the macOS path. Not recommended.

### Recommendation

A, in two steps, with C's ADR corrections done now regardless (they are facts,
not policy). Do not start B unless a confined process on the unconfined
loopback path becomes a real case: agent scope already has its own mode, and
tent/lima and the like are separate containment layers.

### Smallest first slice

Bridge-side only, default off, no host or manifest change: an optional token
read from the bridge's environment (`CLOWN_BRIDGE_TOKEN`); when set, every
request must carry `Authorization: Bearer <token>` (constant-time compare, 401
otherwise, no body), when unset behaviour is exactly today's. Tests: 401
without and with a wrong token, 200 with it, `/healthz` included, and the
unset case unchanged. Second slice: the host mints the token, sends it on its
own calls, and adds the manifest header, after the claude `headers` check.
I did **not** implement this slice: it is security-relevant, and the brief
says to leave that for a ruling.

### Questions for the operator

1. Is the threat model "other users and confined processes on the same host"
   (then A), or "single-user developer host" (then C)?
2. Should the token be per bridge or per session? (Per bridge limits what a
   leaked one reaches; per session is one value to thread.)
3. May I verify claude's `headers` support on `http` entries with a throwaway
   server (no repo changes), before the second slice?
4. Should `/healthz` stay unauthenticated so an external probe works? (It
   leaks only whether the child is alive.)
